# 44.2.0 plan — architecture items ahead of the 45.0.0 rebase

Status: decided 2026-09-26 — a grill pass settled every open item; items 1-3
and 5 implemented and CI-proven the same day. Companion to
[fedora-45-rebase.md](fedora-45-rebase.md)
(the base move itself) and [peer-distros-research.md](peer-distros-research.md) (where
each idea comes from). Everything here is base-independent: it works identically on a
Fedora 44 image, which is the point — land the features on the stable base, keep
45.0.0 a rebase-only release where any regression is attributable to the base move.

Contract basis: the versioning rule says the minor and patch "carry kuma's own"
changes on the named Fedora base (docs/contract.md:9), and "additions are free" —
new verbs, flags, doctor checks, optional keys (contract.md:61-62). Every item below
is an addition except item 5, which is a deprecation note and follows the announce-
then-flip rule (contract.md:64-67). Nothing here touches the declaration schema.

## 1. Exit bootc-image-builder for VM disks (the qcow2 path)

The last load-bearing BIB surface. `kuma vm`/disk builds hand the image to the frozen
`quay.io/centos-bootc/bootc-image-builder:latest` for a qcow2 (main.rs:2287-2300,
BIB_IMAGE at main.rs:77); releases already attach the BIB-free live ISO instead
(release.yml:19). Replace the disk half with kuma's own installer:

- Create a sparse raw image, `losetup -fP` for a partition-scanning loop device, and
  run the same partition + `bootc install to-filesystem --skip-finalize` script real
  installs run (partition.rs:815-831) against `/dev/loopN`, then detach and
  `qemu-img convert -O qcow2`.
- The install script already runs against arbitrary block devices and already boots
  under QEMU in CI (the install job installs onto a virtual disk inside a guest);
  the loop device is the same surface with the VM removed. LUKS needs no new code —
  cryptsetup runs on the loop device like on any disk; the `--esp`/`--boot` size
  flags carry over; the "refuses a disk with anything on it" check sees a fresh
  sparse file and passes.
- Payoff beyond dependency removal: the CI install job's comment records that the
  boot job's disks are ext4 BIB output, so every btrfs-only path — the convergers,
  the snapshots, the ordering-cycle assertion — goes unbooted there (ci.yml:264-273).
  VM disks built by kuma's own installer are btrfs-root like real machines, so the
  daily boot heartbeat exercises the real layout, which is exactly what the 45 rebase
  test plan leans on (snapshot/hibernate items against installed 45 machines).
- Design, settled 2026-09-26: qcow2 is the only output — no `--format raw` (nothing
  consumes raw; the loop-device intermediate is raw regardless, and a format flag is
  free to add when something asks). And the BIB path is replaced outright, no legacy
  flag for one release — `kuma vm` disks are not published artifacts, the verb, flags
  and output keep their meaning, and the image-id stamp semantics (main.rs:2296-2298)
  survive unchanged. The output stays `qcow2/disk.qcow2`, so smoke.sh:3047 and
  main.rs:2262 do not move either.
- Test plan: smoke `--install --boot` against a kuma-built qcow2 (btrfs assertions
  active, not silently absent); LUKS + swapfile variant; the image-id staleness
  warning; fstrim keeps the image sparse after conversion.

## 2. Convergence-timer guardrails (battery, metered connection)

The daily timer carries flatpak/brew installs and fires on a sleeping laptop's
`Persistent=true` catch-up whether the machine is on battery or a metered connection
(blocks.rs:565-575). The timer semantics are already right (Persistent,
RandomizedDelaySec, network-online ordering, retries, low CPU/IO weights —
blocks.rs:543-560); what is missing is the gate uupd ships
(https://github.com/ublue-os/uupd): battery threshold and metered-connection pause.

- Gate inside the converger entry (a pre-flight in the sync script or a small
  `kuma sync --gate` check the service runs first), not in the timer: the decision
  needs live power/network state, and the service is where retries already live.
- Battery: skip when on battery power below a threshold (uupd: 20%); the checks are
  `/sys/class/power_supply` reads, no daemon required.
- Metered: read NetworkManager's `Metered` property (busctl/nmcli), not a GNOME
  setting — kuma is desktop-agnostic and NM is on every kuma image. uBlue documents
  the GNOME toggle as the user-facing pause switch
  (https://docs.projectbluefin.io/administration/); reading the NM property gives
  the same switch to niri and COSMIC machines for free.
- The kuma-specific half none of the peers have: convergence is a *promise*
  (README: converge at boot and on a daily timer), so a skipped run must be recorded
  and surfaced, not swallowed. Write a skip stamp beside the existing stamps in
  `/var/lib/kuma/`, and grade it in `kuma doctor`: "convergence skipped N runs: on
  battery / metered" as an informational check. `kuma sync` always runs ungated —
  the gate is the timer's, never the verb's.
- Scope cut: uupd's per-run network byte budget and CPU/mem checks are not adopted —
  the byte budget needs accounting infrastructure for marginal value, and CPU/IO
  weights already bound the storm (blocks.rs:499-511).
- Test plan: unit tests for the gate's decision table (AC/battery/metered matrix);
  a golden asserting the service wires the gate; doctor's new check in the goldens.

## 3. Install provenance at the physical root

bootc writes `.bootc-aleph.json` recording the source image ref+digest and install
facts (https://github.com/bootc-dev/bootc/blob/main/docs/src/bootc-install.md).
Kuma's image carries the declaration (concepts.md:138), but it cannot carry
install-time facts: which base digest `kuma.lock` resolved to that day, what media
installed the machine, when, with which kuma. Add `/var/lib/kuma/install.json`,
written by `kuma install` on the target — the installer already writes
`/var/lib/kuma/user` and `/var/lib/kuma/hostname` onto the target the same way
(main.rs:3401, install.rs:152-153). Fields: declaration hash, resolved base digest,
media source (LIVE_SOURCE's answer, liveiso.rs:64-76), kuma version, install date.

- Readers: `kuma doctor` (self-description, the "installed by" answers),
  `kuma diff` (base moved since install). `kuma.lock` stays the build-resolution record; this is
  the install record, and the two answer different questions.
- Scope note, decided in implementation: diff's "base moved since install"
  did not land. A machine carries no lock — the current base digest lives
  beside the config on whatever built the running image — so the only
  machine-answerable comparison is "the image moved since install", which
  bootc's own deployment history already shows. doctor is the reader the
  file has; recording the install image's ref+digest alongside the base
  digest keeps the door open without pretending a reader exists.
- Absence is silent, decided 2026-09-26: doctor and diff surface the file only where
  it exists. Every machine that updates into 44.2.0 will never have one — absence is
  ambiguous (pre-44.2 kuma install vs never-kuma) and unrecoverable, so printing it
  would be a permanent informational nag on the machines the contract cares most
  about, for a fact nothing can act on. Omitted, not pasted as "not recorded" — the
  same rule inspect.rs:980 draws.
- Live media writes the same file for the *pulled* image — the distinction matters:
  the media is not what lands on disk (liveiso.rs:32-36), and the provenance file is
  where that distinction becomes inspectable.
- Test plan: install-assertion in the smoke install stage (file exists on the
  target, digest matches the staged image); doctor surfaces it; restore path leaves
  it consistent.

## 4. Digest-pin the frozen BIB image — shipped

Landed in 44.0.1: the digest pin at main.rs:90-91, with the archive date and the
reasoning in the const comment at main.rs:77-89. Kept here as the record. Item 1
landing shrinks the pin's consumer to the legacy anaconda-iso path, which is the
point: the frozen dependency should be as small as the frozen thing it names.

## 5. Deprecate the BIB anaconda-iso default (note + warn, flip in 45.0.0)

`kuma iso` without `--live` builds BIB Anaconda media (main.rs:249-259) that
strangers do not download — releases attach the live ISO (release.yml:19,327) — and
Anaconda's manual partitioning buys nothing against kuma's fixed three-partition
model (the reason Bazzite keeps legacy ISOs is a case kuma deliberately does not
have, README "Not yet").

- Contract handling: verbs keep "the same meaning" forever (contract.md:45-46), so
  44.2.0 names the deprecation in the changelog ("what to use instead: `--live`")
  and warns in output; the default flips in 45.0.0 — announce-then-flip, never the
  same release (contract.md:64-67). The ISO's on-disk layout is explicitly not an
  interface (contract.md:83-84), so the live ISO side needs no ceremony.
- The warn should carry the one real trade-off: live-install pulls the image over
  the network by design (liveiso.rs:32-36). If a no-network installer is ever
  wanted, it is a new flag, not this default.

## 6. Tracked, not scheduled — settled 2026-09-26

- greenboot-rs (F46+ when Fedora bumps past 0.15.x; F45 ships 0.15.8 —
  peer-distros-research.md §2).
- bootc `--download-only` staging: dropped — `kuma update` rebuilds a local image,
  so bootc's staging verbs don't map; the base prefetch is the only stageable part
  and `kuma update --check` already answers the cheap half.
- SBOM/attestation publishing: tracked, deliberately out. Adopting it reverses the
  documented no-SBOM stance (contract.md:111-114, SECURITY.md) — a contract decision
  to make with SECURITY.md open, not a rider on this release.
- Release screenshots: cut, not adopted. A screenshot already ships in-repo
  (docs/screenshots/niri.png), and CI's console logs, greeter verdicts and boot_id
  assertions are the release evidence; screenshots would duplicate it cosmetically.
- Support-tiers doc and the akmods lane: both parked as named 45.0.0 planning
  decisions, taken together — the tiers are mostly about the NVIDIA stance, so
  writing one before deciding the other means writing it twice. 44.2.0 commits to
  nothing either way on both.

## Sequencing note

Item 1 first: it is the risk item and it upgrades the daily boot heartbeat that
every later item and the 45 rebase itself lean on. Items 2-3 and 5 are independent
and cheap. Item 5 is a changelog line, a warning, and a test update. If item 1 slips,
2-3 and 5 still make a coherent 44.2.0 and the qcow2 exit moves to 45.x.

Done is landing-based, no calendar: items 1-3 and 5 implemented, CI green — with the
smoke boot stage's btrfs assertions finally running against kuma-built disks instead
of silently-absent BIB ext4 output (ci.yml:264-273) — and the changelog written.
44.2.0 ships when that is true. If F45 GA arrives first, the rebase waits or proceeds
on a branch; that is cheaper than a rushed disk-format swap.
