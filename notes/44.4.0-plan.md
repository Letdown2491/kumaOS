# 44.4.0 plan — the nostr layer

Status: drafted 2026-09-28. The decisions below were settled in a design
discussion against two source repos — [derekross/opal](https://github.com/derekross/opal)
(the architecture this borrows) and [noctalia-dev/noctalia](https://github.com/noctalia-dev/noctalia)
(the surface it renders on) — and against this codebase, which was read before
any of it was written down. What was decided: build the ideas natively — no
fork of Opal, no packaging of it, kuma owns the code. Niri is the first-class
desktop and noctalia the first-class shell; COSMIC stays experimental and gets
the daemon without the panel. "Ship the feature" is the release bar, not a
spike.

Contract basis: every item is an addition — new verbs, new binaries, new
optional declaration keys, new doctor checks (contract.md:61-62). Nothing
renames or reinterprets; no announce-then-flip applies. The release does not
touch the versioning rule (docs/contract.md:9).

## 0. What the layer is

One user daemon holding a nostr key, answering two kinds of caller: remote
apps speaking NIP-46 (the "bunker"), and local programs speaking a private
protocol on a socket. One CLI that is both the human interface and the
noctalia plugin's transport. One bar widget and one panel, living in a
noctalia plugin baked into the image. One declaration block turning all of it
on. The security posture is Opal's, and it is kuma's posture already: the key
is encrypted at rest, every consequential action is either policy-approved or
asked, every answer is logged, and nothing is a silent pass.

Shipped: 44.4.0 carries this layer with one change of surface. The noctalia
plugin below never shipped — noctalia left the image in the same cycle,
replaced by kuma-shell — and the bar widget and panel landed as kuma-shell's
signer plugin (the kumaui tree's `nostr` and `nostr_panel` modules), shelling
this same CLI against this same daemon. The daemon, the CLI and the
vault, policy, pairing and bunker stack shipped as written; the sections
that describe the plugin itself — its Luau, its transport quirks, its bind —
are the record of a design that was superseded.

## 1. `kuma-nostrd` — the daemon

The package gains a `[lib]` and the binaries become `[[bin]]` targets: `kuma`
(the system tool, untouched), `kuma-nostrd` (the daemon a hardened unit runs),
`kuma-nostr` (the CLI). Shared code moves under `src/nostr/`; the split is
structural, not philosophical — the unit wants a small executable whose surface
an auditor can hold in their head, not a root-oriented monolith.

- **The vault.** The nsec lives in the Secret Service's login collection as
  NIP-49 `ncryptsec` (scrypt, N=2^18 — Opal's measured default). Read through
  `oo7` 0.6.0, the pure-Rust Secret Service client COSMIC itself ships against.
  Import surfaces: nsec, hex, `ncryptsec`, NIP-06 mnemonic, or generate —
  every decoder is already in the `nostr` crate (nips::nip06, nips::nip49).
  New passphrases pass a strength check.
- **Decided 2026-09-28: login-keyring storage with a gate-style lock.** The
  keyring half is already baked — `gnome-keyring` and `gnome-keyring-pam` are
  in the niri set (blocks.rs:34-39) and `pam_gnome_keyring` unlocks the login
  collection at greetd (measured on this machine's /etc/pam.d/greetd). So a
  fresh machine needs no new passphrase UX and no second secret. Lock drops
  the key from memory and refuses; unlock re-reads from the keyring — honest
  about being a gate, not a wall, and upgradeable to an independent-passphrase
  vault later without a schema change.
- **The NIP-46 bunker.** Request loop over NIP-44-wrapped events; both
  connection directions (`bunker://` tokens and `nostrconnect://` links); QR
  via `qrencode` 0.14. Per-app keys, so an app learns the npub only by asking.
- **Decided 2026-09-28: lean transport.** The `nostr` crate (0.45.5) carries
  every protocol piece — nip44, nip46, nip49, nip42, nip65 — but not the
  relay pool; that half of nostr-sdk drags tokio and its async stack into a
  85-dependency lock file with no runtime anywhere in it. What replaces it is
  a few hundred lines: thread-per-relay, blocking WebSocket
  (`tungstenite`), one subscription (requests addressed to the bunker
  pubkey), NIP-42 auth challenges, reconnect with backoff. The transport
  holds no secrets and its one scary failure — the bunker silently stops
  answering — is watched three ways: the doctor's liveness grade, the bar
  widget's offline state, and the smoke stage. The notifications module is
  the honest nostr-sdk moment, if it ever comes.
- **The policy engine.** Opal's model, borrowed whole because it is right:
  per-app Basic (everyday kinds sign unattended) / Ask / Trust; sensitive
  methods always ask — profile, follow, relay-list and mute-list writes,
  deletions, NIP-17 decrypt, auth tokens — and can be remembered for an hour
  at most; an approval shows the exact event before the finger commits; an
  activity log records what was signed and why it was allowed, with a privacy
  mode; a kill switch refuses everything at once.
  **Decided 2026-09-28: a newly paired app defaults to Ask-everything.**
  Opal defaults to Basic, and for a signer a person opts into on purpose the
  strict default is the honest one — relaxing to Basic is one toggle in the
  panel, and the smoke stage asserts that a fresh app asks.
- **The socket.** `$XDG_RUNTIME_DIR/kuma-nostr.sock`, 0600, peer-uid checked,
  newline-delimited JSON. Reaching the socket grants nothing by itself — the
  same sentence Opal says, for the same reason.
- **The unit.** Follows `SHELL_SERVICE` (blocks.rs:1943): `PartOf=` and
  `WantedBy=graphical-session.target`, `Slice=session.slice`, enabled
  `--global` (blocks.rs:3123), `Restart=always` — a bunker that exits zero is
  still a bunker that stopped answering. Hardening per
  [unit-sandboxing.md](unit-sandboxing.md), which this becomes the first user
  unit for: `NoNewPrivileges`, `ProtectSystem=strict`,
  `ProtectHome=read-only` with `ReadWritePaths=` the daemon's own state,
  `RestrictAddressFamilies=` unix + inet, `SystemCallFilter` from the same
  research.

## 2. `kuma-nostr` — the CLI

`setup` (import or generate, passphrase), `unlock` / `lock`, `prompts`,
`approve <id> [--remember 1h]`, `deny`, `apps` / `revoke <id>`,
`bunker --qr`, `status`. Every verb talks to the socket; none reads the key
directly. This binary is also the noctalia plugin's entire world — the plugin
never opens the socket, it shells this (see item 3) — so one IPC shape serves
two consumers, which is the property that keeps the surface auditable.

## 3. The noctalia plugin

Baked at `/usr/lib/kuma/noctalia/plugins/kuma-nostr/` (`plugin.toml` + Luau
entries), declared in the authored config as a `[[plugins.source]]` with
`kind = "path"` — noctalia treats path sources as immutable and does no git
ops on them, which is exactly the shape of a file kuma baked
(docs.noctalia.dev plugins: "ideal for local development or Nix-managed
plugins"). The authored config already carries `[plugins]` policy
(`auto_update = "none"`, asserted at blocks.rs:3090); the source and the
`enabled = ["kuma/nostr"]` entry render only when the declaration block says
so, and the user's `settings.toml` still wins — the same authored-layer /
user-state merge the desktop already runs (blocks.rs:2245-2269).

- **Bar widget:** a glyph with a dot for pending approvals — pulse it while
  one waits.
- **Approval panel:** `onOpen` renders the pending queue (the exact event,
  the asking app, the remember-choices) through the declarative `ui.*`
  vocabulary; every mutation goes through the CLI via
  `noctalia.runAsync(...)` with output capture — Luau has no sockets, and
  that is fine: the plugin is a face, the daemon is the policy.
- **Decided 2026-09-28: toasts point, panels decide.** A transient toast is
  no place for an authorization decision — an accidental click is too easy
  and "remember" has no business there. Toasts (via `noctalia.notify`) and
  libnotify alike say *something wants to sign*; the deliberation happens in
  the panel.
- **The bind:** `Mod+Ctrl+N → noctalia msg panel-toggle kuma/nostr:panel`
  joins the baked binds only when the block renders, beside the launcher and
  lock binds kuma already owns (blocks.rs:2524, 2552). The
  `nostrconnect://` link handler is registered the same way — a desktop
  file and a line in the `mimeapps.list` kuma already stages
  (blocks.rs:3020) — so clicking a nostrconnect link anywhere lands in the
  approval panel rather than in nothing.
- The plugin declares its `plugin_api` level pinned to what the image's
  noctalia supports; the build already proves the baked config merges
  (blocks.rs:3089-3091), and that proof gains a plugin line.

## 4. The declaration block

```toml
[nostr]
enable = true
# relays = ["wss://…"]   # optional public fallbacks, listed after the local relay
# [nostr.relay]          # the local relay ships with the block by default;
# enable = false         # this is its off switch
# policy defaults, lock timeout — optional keys, contract.md:61-62
```

- `enable` gates the whole render: packages (the two new binaries ride the
  image's own build), the unit, the plugin, the bind, the local relay.
  Absent → nothing at all ships, exactly like `[backup]`; `enable = false`
  renders identically and is the explicit form — the same grammar as
  `[snapshots]` and `[backup]`, because a committed file that says
  considered-and-off reads differently from an omission. Toggling off never
  destroys anything: the vault lives in the login keyring and pairings and
  policy live in the daemon's own state, all user state an image update
  does not touch, so a disable is reversible by construction and a
  re-enable finds the old key where it was. concepts.md says so in one
  sentence.
- **`relays` is a list everywhere, and N is the normal case.** The rendered
  list is `[local, …declared]`: declared entries are additional, never a
  replacement, so adding a public fallback cannot silently strip the local
  relay — replacement is spelled, `[nostr.relay] enable = false` plus your
  list. The schema accepts any number, every entry is validated at build
  (a malformed one fails the build, the house rule that a typo is a build
  failure rather than a shrug), and the daemon connects to all of them —
  the transport is thread-per-relay by design, requests are answered
  across the set, and `switch_relays` returns the whole current list.
  Doctor grades liveness per relay by name, so a dead one is visible while
  the rest keep the bunker answering (item 6).
- **`ws://` is accepted only to loopback.** A user already running a relay
  on the machine (development, or a relay of their own on localhost) points
  an entry at `ws://127.0.0.1:…` and the daemon takes it; `ws://` to
  anything else is refused at build — that is plaintext on the wire, and a
  declaration that leaks kind 24133 traffic by configuration is exactly the
  shape of mistake a validator exists to catch. Native local programs keep
  the paired socket as their channel — but WebSocket-native callers (a
  browser app cannot open a unix socket) sign through the local relay at
  `ws://127.0.0.1:<port>`, which is part of why the relay is the default
  rather than an extra.
- **Decided 2026-09-28: the local relay is the default signing path, and no
  public relay is.** The earlier draft defaulted the list to the
  project-run `wss://relay.nip46.com` on the rule that a relay is
  credential-free and shared where a repo is personal, and the rule was
  wrong in both directions: it made a third party the default participant
  in every signature, and it put a public relay's availability on the
  release's out-of-box promise. The new default is self-contained — the
  bunker's first-boot reachability is the machine's own. The relay runs
  kuma's own [nip46-relay](https://github.com/Letdown2491/nip46-relay)
  (MIT, the same binary anyone can host), carrying only kind 24133 and
  24135 traffic, in memory only, evicted after ten minutes — signing
  messages never touch disk on it, and no feed ever crosses it. A user who
  wants the public fallback says so: `relay.nip46.com` (or any other
  relay) joins the list only by being declared, and nothing about its
  availability is promised. What the operator sees is metadata — that a
  bunker is live, which apps connect, when — never a plaintext event,
  which is NIP-44 end-to-end. concepts.md discloses the posture a stranger
  should be able to read: the bunker is reachable by whatever can reach
  the machine — loopback for the callers the socket cannot serve, any
  tunnel the operator runs, and the tailnet when tailscale is declared —
  and what a declared public relay could see. The doctor's liveness grade
  answers "the relay is down," and the reachability fact answers "my phone
  cannot reach it" (item 6). NIP-46's `switch_relays` method exists
  precisely so a relay set can evolve, so a default is an initial value,
  not a permanent one.
- **The daemon generates a dedicated remote-signer key, never reusing an
  imported identity key.** NIP-46 allows the signer keypair and the
  user keypair to differ, and with a shared relay in the list the
  difference matters: the operator then links a pseudonymous bunker pubkey
  to traffic instead of the user's identity. The same opinion Opal holds —
  apps do not learn your npub until they ask — held one layer down.
- **COSMIC: daemon-only.** The block renders the daemon and CLI on
  `desktop = "cosmic"`; the noctalia plugin does not (there is no noctalia
  there). A cosmic applet is tracked, not built (item 9).
- **Refused headless.** The daemon's unit is a user unit under
  `graphical-session.target`, so on a declaration with no desktop the
  `[nostr]` block fails the build saying so — shipping a daemon that can
  never run is a silent pass by another name. A system-level always-on
  bunker on a kuma server is a deployment mode worth wanting and is
  tracked (item 9), not smuggled into this one.
- **Goldens regenerate deliberately, never in CI**
  (containerfile/mod.rs:198-199): a dedicated nostr golden case joins
  GOLDEN_CASES, and `everything-on` grows the plugin COPY lines. The version
  bump itself already showed what forgetting this costs.

## 5. The baked relay — the default signing path

Decided 2026-09-28 to pull into 44.4.0, after the bunker it serves — it is
meaningless before one exists and lands last in the tracer order for the
same reason. Decided 2026-09-28, after the enabled/disabled discussion: the
relay is not an extra layer but the default signing path, and tailscale is
a mode of it, not a requirement — the relay serves whatever can reach the
machine, and exposure beyond loopback is the operator's business. Kuma
already ships tailscaled, so the common case wires itself:

- The relay ships with the block: `[nostr]` on bakes
  [nip46-relay](https://github.com/Letdown2491/nip46-relay) as a user
  service bound to loopback, and `[nostr.relay] enable = false` is the off
  switch — a bunker with no baked relay, connecting only to what `relays`
  declares. When the declaration runs tailscaled, convergence wires
  `tailscale serve` to put the relay on the tailnet with a certificate —
  a runtime action in tailscaled's own state, so the sync machinery
  converges it rather than the image baking it, and absent tailscale
  nothing is refused: the bunker is local-reach-only and the doctor says
  so (item 6). The `ws://`-to-loopback-only rule (item 4) survives
  untouched — the ts.net URL is tailscale's TLS, not ours — and a phone on
  the tailnet signs through the user's own machine with no third party at
  all.
- The daemon's relay list is `[local, …declared]`: local first, the
  `bunker://` QR carries them in that order, and a phone off the tailnet
  falls back to a public relay only if the user declared one. The daemon
  stays a pure client either way — the signer never listens, the relay is
  the listener, and the two keep their own hardening stories.
- **Decided 2026-09-28: the relay is ported to Rust, and the Go build
  question dissolves rather than gets answered.** The original draft asked
  how a Go binary rides a Rust image build — golang in the containerfile,
  or a hash-pinned prebuilt — and both answers were permanent taxes: a
  second toolchain or a second provenance story, forever. The relay is
  small, self-owned, and becoming baked infrastructure on every machine
  with the block, so it is ported into this workspace instead: the same
  behaviors (kind filter, timestamp window, in-memory TTL eviction, rate
  limits) in the language the layer already speaks, sharing the daemon's
  `nostr` crate and `tungstenite` stack. It stays a separate binary with
  the `nip46-relay` name and MIT license, because the signer never
  listens — and "a NIP-46 relay anyone can host" stays true from kuma's
  own repo. The public relay keeps running Go until the port is proven;
  the two are decoupled, and when it migrates is the operator's call, not
  this release's.
- Doctor grades the local relay beside the others: active, answering, and
  whether `tailscale serve` is actually exposing what the declaration says
  it should.

## 6. `kuma check` and doctor grades

New checks, all informational-or-warn, absence silent (the rule the 44.2.0
plan fixed at notes/44.2.0-plan.md:104-109): daemon unit active for a user
with a session; socket answers; liveness — a relay round-trip through the
daemon's own probe, so a dead transport grades instead of waiting for an
angry app; the vault decrypts; N apps paired, and any app holding Trust
grades Warn by name — a standing grant is the loudest thing in the layer and
doctor is where it stays visible; and the reachability fact stated plainly —
a bunker whose only relay is the local one says "local-only," or
"tailnet-only" when tailscale serves it, because an off-tailnet phone
showing a dead bunker needs the why, not just the symptom.
`kuma doctor` reads; it never nags.

## 7. Tests

- **Offline unit tests** for everything pure: the policy decision table
  (policy × method × remembered-answer × locked), NIP-49 round-trip, socket
  framing, URI builders. The suite stays offline, like all of kuma's.
- **The relay harness, in two phases.** First the Go
  [nip46-relay](https://github.com/Letdown2491/nip46-relay) bootstraps the
  lane — the daemon needs a real relay to be tested against before the
  port exists. Then the Rust port lands with an **equivalence proof**: the
  same scripted NIP-46 client run against both binaries, asserting the same
  behavior — kind filter, timestamp window, eviction, rate limits — and the
  port becomes the fixture from then on. Interop covers connect, sign,
  NIP-44 both ways, reject-on-policy, and the relay's own eviction and
  rate-limit behavior. Opal proves the shape (its tests/interop drives
  `nostr-tools` BunkerSigner); ours drives a scripted client in the same
  spirit.
- **The smoke stage:** the published-image guest boots, the daemon starts
  headless (`systemctl --user start` — the unit is `WantedBy=`
  graphical-session.target, not dependent on one), a scripted local app pairs
  over the socket, signs against the CI relay, a refused method grades the
  refusal, lock/unlock holds, and the activity log answers for all of it.
- **Cross-version honesty:** the "bunker survives an upgrade" assertion —
  install old, upgrade, keyring intact, pairing intact — cannot run until
  44.5.0, because 44.4.0 is the first release with a layer to upgrade from.
  The assertion is written now and gated on the previous release carrying
  the daemon, so it wakes itself.
- **The guest stderr hole** that made the cosign incident blind
  (smoke.sh:998 `guest()` discards ssh stderr) is fixed before this stage is
  written, not after it fails once.
- The image audit (`scripts/publish-audit.sh`) sweeps the new staged files
  with no new machinery; the goldens are the review.

## 8. Docs and SECURITY

concepts.md owns the `[nostr]` essay (the layer, the vault, the policy
model); desktops.md gains the plugin and the bind; the glossary carries
bunker, nsec, ncryptsec — one line each. SECURITY.md needs the nsec trust
model written down before the first image ships: what holds the key, what
unlock means, what a paired app can do, what the sandbox bounds. That is a
contract decision with SECURITY.md open, and it gates the release rather
than trailing it.

## 9. Tracked, not scheduled

- **A headless always-on bunker.** The same software as a system service —
  a kuma server as a machine's standing signer. Refused by the build for
  now (item 4); it wants a system unit, its own hardening pass, and a
  provisioning story for a machine with no session, and it is the least
  baked idea on this page.
- The notifications module (NIP-17 DMs, mentions, zaps): the second consumer
  of the relay loop and the natural nostr-sdk conversation.
- `kuma` as a paired local app — release announcements signed through the
  bunker rather than holding a key. The dogfood that proves the pairing API.
- A COSMIC applet, when cosmic stops being experimental in this repo.
- The independent-passphrase vault, if the gate-style lock proves too soft.
- Status/scrobble (NIP-38): the third Opal module, furthest from kuma's
  system shape.

## Sequencing

Vault first — it is offline-testable and everything else needs it. Then
socket + CLI (the verbs make the daemon drivable before it is wise). Then
NIP-46 against the relay harness, then the policy engine hardening it. The
plugin follows the CLI — it cannot precede the verbs it drives — and the
declaration block is next because it only renders what already exists. The
relay is still last in the tracer order — it is meaningless without a proven
bunker — but as the default signing path it is no longer a rump: its port's
equivalence proof and its smoke stage sit on the release's critical path,
not beside it. The smoke stage and doctor grades land with what they grade,
not after.

Done is landing-based, no calendar: items 1-8 implemented — the baked
relay included, because the release ships when the work is proven, not
when a date says so — with the unit and interop tests green in CI,
goldens regenerated and read as the diff they are, SECURITY.md carrying
the trust model, and the changelog written. 44.4.0 ships when that is
true.

## Postscript — the first real week (2026-09-29)

The plan imagined the design; the first days of use corrected it. What
the release carries that the plan did not know:

- **The worker's runtime is its own.** The plan never named a thread
  topology, and the first URI connect by relay wedged the daemon whole:
  the worker's keyring burn rode a handle to the main thread's runtime,
  which `serve()` had parked — a future waiting on a poll that never
  comes, holding the daemon lock. The rule now written in the code and
  in AGENTS.md: every thread that block_on's a future drives a runtime
  built on itself; nobody borrows a parked runtime's drivers.
- **The panel is only as honest as its failures are loud.** A working
  revoke looked broken because the panel repainted over errors in
  silence; a failed fetch emptied the list because the empty state
  impersonated it. Errors surface, failures keep last-known state.
- **The noctalia host's loaded facts** (all measured, in AGENTS.md):
  the flex cross-axis default is center (the docs page is wrong, the
  example plugin's notes are right); a clickable container is wrapped
  content-sized; `NoDisplay` hides a handler from the portal, which is
  where flatpak browsers look; free text rides argv, never a shell
  line; a local read before its declaration is nil.
- **The verbs grew where the plan's nouns were wrong.** Revoke turned
  out to be a ban, not a removal — `delete` is the removal people
  meant, `revoke` keeps the tombstone, `unrevoke` the way back. The
  client's own handshake metadata (the spec's connect fields) names
  apps; a name derived from the claimed url fills the silence; the
  strict event parse that called every odd-shaped event unreadable is
  retired from summary, sensitivity and signing alike — what the
  person approved is what gets signed.
- **The autologin caveat, measured**: the gate model's keyring is
  PAM-opened at a real login; an autologin boot starts the daemon
  locked until the keyring is opened. The honest posture holds, the
  docs say so, and the inactivity switch's default rationale names it.

## Postscript — the release week (2026-10-02)

The layer shipped as 44.4.0 and the release tier did its job: the
binaries and the ISO went out, and the image tier failed where the
binaries could not carry it. What the release week found:

- **The aleph failure was ours, and the dates were a shadow.** Fresh
  installs of kuma's images died in `bootloader-update.service`:
  `rpm-ostree compose image` emits no version label, bootc's install
  wrote `"version": null` into `/sysroot/.bootc-aleph.json`, and
  bootupd's reader requires a string. The float was blamed and the
  compose environment pinned to a mirror of the last good float; a
  recompose under the pinned env proved its tools byte-identical to
  the floating one's, which moved the suspicion to kuma's own
  Containerfile and the version label it never stamped. Stamped
  (9a16b14), the failure vanished on every base. The pin rose and fell
  inside a week; the mirror job went with it (8c2284a). The released
  binaries never carried the bug; the released ISO does, and whether
  to retag it or cut 44.4.1 stays open.
- **Filed upstream as a contract bug, not a kuma one**: the writer
  declares `version` optional and emits null; the reader requires a
  string. [coreos/bootupd#1166](https://github.com/coreos/bootupd/issues/1166) —
  any pipeline that composes label-less hits this on every boot.
- **The smoke's real-session section learned what a displayless VM can
  answer.** The shell survived the GPU-less VM in restart-waves until
  the unit's start limit ended them, so every probe that needed a live
  shell process — notification ownership, the sleep-inhibitor
  readback, a stale noctalia pgrep — either measured the runner's
  timing or passed vacuously. What remained asked the wiring and the
  journal; whether the shell draws is real hardware's question. The
  measured facts are in AGENTS.md. Partially re-armed 2026-10-03:
  kumaui's idle-without-windows fix (e90884c) keeps the shell alive
  holding its DBus names through output loss, so the notification-
  ownership probe came back and passed CI the same day. The sleep-
  inhibitor readback stayed retired, and for a different reason than
  the wave era: the shipped sleep guard's own prose says kuma-shell
  holds no logind delay inhibitor by design — a hung shell cannot
  stall sleep the way the hung noctalia could — so that check asserted
  noctalia's contract and was the last fossil of the swap.
