# 45.0.0 secret-service research — stay on gnome-keyring or adopt oo7

Status: research written 2026-10-29, the day oo7's post-beta stable updates
finished pushing to F45 (0.7.0~beta-4, then `beta^1.e91b98a-1`) and six days
before Fedora 45's current GA target (2026-11-03). Companion to
notes/fedora-45-rebase.md (the rebase pass, which deferred this question to
"the oo7 decision") and notes/45.0.0-upgrade-path-research.md. This file
answers it against primary sources: the F45 Everything repodata, extracted
F45 RPM payloads (/tmp/opencode/oo7-rpms/), upstream git, Fedora change
threads, blocker-review tickets, bugzilla, and this repo's own code. Labels:
CONFIRMED = verified from a primary source on 2026-10-29 unless noted;
REPORTED = secondary source or a claim read in a thread but not reproduced;
BETA-STAGE = verified against an F45 RC-era build, can still move by GA;
UNVERIFIED/UNKNOWN = no source found.

## Verdict

**Stay on gnome-keyring for 45.0.0. Adopt oo7 in a later release, once F45's
own ride shakes out.** The case, in order of weight:

- **The stay-lane is confirmed working on F45 as shipped.** Both greeter
  stacks this image uses — greetd's and cosmic-greeter's — still carry the
  `pam_gnome_keyring.so` lines on their auth and session stacks in the RC-era
  payloads, alongside new pam_oo7 twins, and the `-` prefix makes a missing
  module skip silently, so both modules coexist and gnome-keyring keeps
  winning the unlock. gnome-keyring 51.1 is still packaged in F45 and its
  upstream is active. `keyring_pam()` (blocks.rs:452-456, already fixed for
  the /usr/lib/pam.d move in `8906e62`) passes unchanged. CONFIRMED.
- **The adopt-lane inherits oo7's two kuma-shaped upgrade bugs.** First,
  unencrypted/passwordless login keyrings fail migration outright ("File
  header doesn't match FILE_HEADER", rhbz 2538274, still NEW on 2026-10-27) —
  and this image supports autologin, which is exactly what produces a
  passwordless keyring. Second, `oo7-daemon.service` enablement rides RPM
  user-unit scriptlets with no preset file, which do not apply on
  ostree/bootc deploys — Silverblue 44→45 upgrades were left with the daemon
  disabled and secrets broken (thread 202421). Both are the failure modes a
  bootc image that ships oo7 would hit. CONFIRMED.
- **oo7 upstream is at a beta.** The crates and daemon ride tag
  0.7.0.beta (pushed 2026-10-29); the fixes Fedora is shipping — login
  keyring lock race, name-claim race, elogind support, the unencrypted
  migration — all landed in main after that tag (catalog: rhbz 2560362#c2).
  F45's own package moved three times inside October. CONFIRMED.
- **Staying costs nothing technically.** The vault in this tree speaks
  spec-level `org.freedesktop.secrets` over zbus 6 and already handles both
  daemon dialects (commit `6de80bc` dropped the oo7 client crate over the
  RustSec zvariant 5.x advisory, repo issue #51); kumaui's ashpd use is
  file-chooser only. Either lane works for consumers; the decision is purely
  about which daemon ships in the package lists. CONFIRMED.
- **gnome-keyring is not going away under us.** It cannot be retired from
  Fedora while NetworkManager-vpnc-gnome, cinnamon, mate-screensaver, sugar
  and friends still require it (rhbz 2549612), and 51.1 released 2026-09-17
  with upstream activity as late as 2026-10-28. CONFIRMED.

The switch seam, when the adopt-lane day comes, is small and named in "What
this repo must do" below. Nothing about the rebase forces it now.

## 1. What oo7 is

- A Rust reimplementation of the freedesktop secret service, at
  https://github.com/linux-credentials/oo7. Components, read from the repo's
  tree and README: **oo7-daemon** (the service that claims
  `org.freedesktop.secrets`), **oo7-portal** (the portal half for sandboxed
  apps), **oo7-cli** (command-line client), the **oo7 client library**
  (the crate), **pam_oo7** (the PAM module that unlocks the keyring at
  login), **cargo/git credential helpers**, and a **kwallet migration
  tool**. CONFIRMED.
- It exists to replace gnome-keyring's daemon role; gnome-keyring's storage
  is what it migrates from. The Fedora change proposal (thread 195274)
  frames it as swapping the default secret service for the release.
  CONFIRMED (thread text).
- Maturity: latest tag 0.7.0.beta; the project is single-repo, actively
  pushed (last push 2026-10-29), 435 stars. Not a 1.0. CONFIRMED.

## 2. What Fedora 45 ships

- **Both secret services are packaged in F45.** The dev repo carries
  gnome-keyring-51.1-1.fc45 and gnome-keyring-pam-51.1-1.fc45 (built Oct 2)
  AND oo7-cli, oo7-daemon, oo7-portal, pam_oo7 — all `0.7.0~beta-3.fc45`
  (built Oct 24, after RC 1.2). Since then two stable updates pushed to F45:
  `0.7.0~beta-4` and `0.7.0~beta^1.e91b98a-1` (2026-10-29). CONFIRMED
  (repodata + Bodhi via rhbz 2560362).
- The change proposal ("Replace gnome-keyring with oo7 as the default secret
  service", https://discussion.fedoraproject.org/t/195274; owners Neal
  Gompa, Fabio Valentini, Michel Lind) is tagged **"Blocks release? Yes"**.
  It claims automatic migration of existing keyrings on upgrade, a comps
  swap for the desktop environments, and adjusted desktop package
  dependencies. CONFIRMED (thread text read in full); the comps PR itself
  (releng/fedora-comps #1326) was not independently fetched — REPORTED.
- What the swap means in practice for a stock F45 desktop: oo7-daemon is
  pulled in as the `org.freedesktop.secrets` owner; gnome-keyring stays
  packaged for its remaining dependents (§6). BETA-STAGE (composes kept
  moving through the freeze; the final GA compose is not out).
- A second thread (https://discussion.fedoraproject.org/t/202421) documents
  the change's first real upgrade casualty on **Silverblue**: after 44→45,
  `oo7-daemon.service` was left **disabled**, secrets were broken, and
  `systemctl enable --user --now oo7-daemon.service` fixed it — migration
  then worked. Root cause: the enablement rides RPM user-unit scriptlets
  (below), which don't apply on ostree-style deploys. CONFIRMED (thread,
  reproduced by the reporter; consistent with the RPM payload, §3).
- The change is running through the blocker process with multiple accepted
  freeze exceptions — see §4. "Blocks release? Yes" has been earning its
  tag: this is the churniest corner of F45. CONFIRMED (blocker tickets).

## 3. The PAM module and the greetd flow

How the password gets to the keyring, and what this repo already checks.

- **kuma's assert today** (`keyring_pam()`, src/containerfile/blocks.rs:
  452-456): `test -f /usr/lib64/security/pam_gnome_keyring.so && grep -q
  pam_gnome_keyring /etc/pam.d/{service} /usr/lib/pam.d/{service}` — module
  present, stack references it, either directory accepted since F45 moved
  vendor stacks to /usr/lib/pam.d (notes/fedora-45-rebase.md §1,
  `8906e62`). CONFIRMED (source).
- **The F45 greetd payload** (greetd-0.10.3-12.fc45, extracted): ships
  `/usr/lib/pam.d/greetd` and a new `greetd-greeter` subpackage. The stack
  keeps `-auth optional pam_gnome_keyring.so` / `-session optional
  pam_gnome_keyring.so [auto_start]` **and adds pam_oo7 twins** on the same
  stacks. CONFIRMED (payload inspection).
- **The F45 cosmic-greeter payload** (cosmic-greeter-1.10.0-3.fc45):
  `/usr/lib/pam.d/cosmic-greeter`, same shape — pam_gnome_keyring lines
  kept, pam_oo7 twins added. cosmic-session-1.10.0-2.fc45 Requires nothing
  secret-related. CONFIRMED (payload inspection).
- **The `-` prefix is what makes the stay-lane safe**: PAM skips a missing
  module silently, so both stacks work whether the image ships
  gnome-keyring-pam, pam_oo7, or both. It is also why kuma must list
  gnome-keyring-pam explicitly — neither greeter package Requires or
  Recommends either PAM module, and without the listed package every
  keyring-using app prompts on launch (the blocks.rs comment at lines
  33-36 says exactly this). CONFIRMED.
- **pam_oo7's flow is different in kind**: it hard-Requires oo7-daemon
  (and the daemon Requires the matching pam_oo7 — version-locked, they must
  ride together), and when the daemon's socket is absent at login it starts
  `/usr/libexec/oo7-daemon-login` to do the unlock. The daemon's encryption
  password arrives as a systemd credential — its unit carries
  `ImportCredential=oo7.keyring-encryption-password`, and the README
  documents `~/.config/credstore.encrypted` under systemd-creds. So the
  PAM module is not just an unlocker, it is the password-feeding half of
  the credential plumbing. CONFIRMED (RPM payloads: deps, units, README).
- **oo7-daemon's units** (`oo7-daemon.service` plus the
  `dbus-org.freedesktop.secrets` alias, both user units): `Type=dbus`,
  `BusName=org.freedesktop.secrets`, `[Install] WantedBy=default.target`.
  **No preset file ships.** Enablement is done by `%systemd_user_*`
  scriptlets guarded on `$1 -eq 1` (first install only) — the pattern that
  provably fails on ostree upgrades (§2, thread 202421) and does nothing
  meaningful in a Containerfile chroot either. A bootc image wanting oo7
  enabled must ship the enablement itself. CONFIRMED (payload inspection).
- NixOS prior art for the wiring: nixos/modules/security/pam.nix has
  `cfg.oo7.enable` wiring `pam_oo7.so` onto auth/session/password stacks
  (https://github.com/NixOS/nixpkgs/blob/master/nixos/modules/security/pam.nix).
  CONFIRMED. Not directly reusable (non-PAM-file-based config), but it
  documents the module's expected placement.

## 4. The F45 blocker list and what upgrades do to existing machines

The blocker-review tickets (https://forge.fedoraproject.org/quality/
blocker-review, read 2026-10-29) and bugzilla tell one story: the oo7
change works on fresh installs and breaks in specific ways on upgrades.

- **#2162 / #2163** — greetd / cosmic-greeter sessions don't unlock the
  oo7 keyring at login. **Accepted BetaFreezeException** (both). CONFIRMED.
- **#2208** — cosmic-greeter's PAM file was missing the pam_oo7 lines
  entirely (a bad patch hunk dropped them); fixed in cosmic-greeter
  1.10.0-3. **Accepted FinalFreezeException.** CONFIRMED — and the reason
  the payload check in §3 matters: the stack contents are exactly the kind
  of thing a rebuild can change under a constant package version.
- **#2225** — after a 44→45 upgrade, **gnome-keyring-daemon is still
  running** alongside (or instead of) oo7. **Accepted
  FinalFreezeException, 2026-10-20.** Dual-daemon state on upgraded
  machines. CONFIRMED.
- **#2245** — SSH passphrases not unlocked after upgrade (rhbz 2558595);
  unvoted as of 2026-10-28. CONFIRMED (ticket state).
- **#2186** — oo7-portal missing after upgrade. CONFIRMED (ticket);
  **#2243 / #2221 / #2244** — further upgrade-flow reports, read but not
  individually load-bearing here. CONFIRMED (tickets exist and are open).
- **rhbz 2538274** — the one that maps to this image: an **unencrypted or
  passwordless `login.keyring`** (what autologin produces) fails migration
  with "File header doesn't match FILE_HEADER" and the keyring is
  effectively lost to oo7. Still NEW 2026-10-27. CONFIRMED (bugzilla).
- **rhbz 2560362#c2** (validation notes, Oct 25) catalogs what landed in
  oo7 main after the 0.7.0.beta tag: PRs #580, #542/#577/#619, #606
  (elogind/logind), #581 + PR #594 (name-claim race), PR #615 (login
  keyring locked race), and issue #572 with commits b236c6fb / 78bb59f
  (the unencrypted-keyring migration fix). These are what beta-4 and the
  `beta^1.e91b98a-1` snapshot (Oct 29) carry. CONFIRMED (bugzilla comment
  + Bodhi). The migration fix shipping is the necessary condition for the
  adopt lane; it is *days* old.
- Other oo7 bugs on file, not blockers for this image but real:
  rhbz 2537728 (oo7-daemon fails under staff_u SELinux, NEW),
  2549684 (Flatpak file backend), 2552171 (GVFS ssh passphrases — fixed in
  gvfs-1.62.0-4.fc45, rejected as blocker), 2556316 (MATE). CONFIRMED
  (bugzilla).
- Upgrade-path framing for this repo specifically: a kumaOS 44→45 ride
  carries `/etc` and the home dirs across (notes/45.0.0-upgrade-path-
  research.md). On the stay-lane the carried state is a gnome-keyring
  login collection unlocked by the same PAM lines — the quiet path. On an
  adopt-lane, that same carried state is rhbz 2538274's input. CONFIRMED
  (by construction from the two sources).

## 5. What consumes the secret service in this image

- **Package lists**: `gnome-keyring` + `gnome-keyring-pam` in the niri set
  (src/containerfile/blocks.rs:32,37) and the cosmic set (blocks.rs:212-213),
  each with the comment explaining the `-` prefix and the silent
  no-module failure. These four lines are the whole package-level seam.
  CONFIRMED (source).
- **The vault** (src/nostr/secrets.rs, src/nostr/vault.rs): speaks
  `org.freedesktop.secrets` over zbus 6 and handles **both daemon
  dialects** — gnome-keyring's `(aoao)` SearchItems result and bare-arg
  Delete, oo7's strict variants. Commit `6de80bc` (2026-10-23) dropped the
  oo7 client crate over the RustSec advisory on its zvariant 5.x dependency
  (repo issue #51) and went spec-level instead. The gate design relies on
  the login collection being PAM-unlocked, which either module provides.
  **The vault needs zero changes in either lane.** CONFIRMED (source).
- **kumaui** (~/Documents/kumaui): ashpd 0.13 used only for the file
  chooser; no keyring client anywhere in the five binaries. CONFIRMED
  (tree read 2026-10-29).
- **Host F44 reference**: gnome-keyring-50.0-1.fc44 + gnome-keyring-pam
  installed, no oo7 packages present — today's shipped state, for the diff.
  CONFIRMED (`rpm -q`).

## 6. Security and maintenance posture, both sides

- **gnome-keyring is alive, not deprecated.** Upstream tags through 51.1
  (2026-09-17), activity as recent as 2026-10-28; Fedora cannot retire it
  while NetworkManager-vpnc-gnome, cinnamon, mate-screensaver, sugar etc.
  still require it (rhbz 2549612). The F45 change moves the *default*,
  not the package's existence. CONFIRMED (gitlab + bugzilla).
- **oo7 is a single-maintainer-shaped bet with a young surface area**: one
  repo, one active tag series (0.7.0.beta), a rewrite of security-critical
  credential plumbing still accumulating race fixes (§4's catalog: two
  login-time races fixed post-tag). Its hardening story is real — the
  shipped units are hardened, and the systemd-creds/credstore design
  (§3) is more modern than gnome-keyring's — but "more modern" and "been
  through a release cycle" are different properties, and F45 is its first
  default-ship. CONFIRMED (repo + payloads) / the last clause is
  inference from the ticket timeline.
- **SELinux on oo7 is not clean**: rhbz 2537728 (oo7-daemon fails under
  staff_u) is open, and this image is a selinux-targeted appliance. The
  dv/policy corner is exactly where a brand-new daemon gets surprised.
  CONFIRMED (bugzilla) / severity to kuma UNKNOWN (staff_u is not this
  image's context, but it is the only data point).
- **NixOS adopted the PAM module** (`cfg.oo7.enable`), which is decent
  third-party validation of the module's shape (§3). CONFIRMED.

## What this repo must do

### Stay lane — 45.0.0

1. **No package change.** Keep `gnome-keyring gnome-keyring-pam` at
   blocks.rs:32/37 and 212/213. gnome-keyring 51.1 is in the F45 repo and
   the greeter stacks keep the lines the build asserts.
2. **`keyring_pam()` stays as-is** (post-`8906e62` form). Verified against
   the RC-era greetd-0.10.3-12 and cosmic-greeter-1.10.0-3 payloads: the
   grep target still exists in both stacks. No goldens change.
3. **On the first 45 build, check the lockfile for oo7 packages** — the
   change swapped comps and desktop deps, so a transitive pull is possible
   even though nothing in our lists wants it. If oo7-daemon sneaks in, the
   `org.freedesktop.secrets` claim becomes a race (and blocker #2225's
   dual-daemon state is the shipped symptom). One `rpm -q oo7-daemon` in
   the built image settles it.
4. **Watch for gnome-keyring retirement signals** (the devel list,
   rhbz 2549612's resolution) as the trigger to re-open this note for the
   46 cycle — not a 45.x event unless Fedora forces one.

### Adopt lane — a later release, when ALL of these hold

Preconditions: F45 GA (target 2026-11-03) plus a soak; oo7 ships a
non-beta release containing the post-beta fix set (the unencrypted
migration fix from issue #572 is the load-bearing one for autologin
machines); the preset/enablement gap below has an upstream answer or a
proven bootc idiom.

1. **Swap the packages** in both lists (blocks.rs:32/37, 212/213):
   `gnome-keyring gnome-keyring-pam` → `oo7-daemon pam_oo7`. They are
   version-locked against each other and must ride together in every lock
   regeneration.
2. **Rewrite `keyring_pam()`** to assert `/usr/lib64/security/pam_oo7.so`
   and grep the greeter stacks for `pam_oo7` (same two-directory form) —
   then **regenerate the goldens**, which pin the assert bytes and the
   dnf install lines. Do not assume the F45 stacks keep the pam_oo7
   twins; #2208 proved a rebuild can drop them.
3. **Ship the daemon's enablement in the image.** The RPM's
   `$1 -eq 1` user-unit scriptlets don't apply on bootc deploys and no
   preset file ships (§3). Bake the user-unit enablement into the layer —
   a user preset file for `oo7-daemon.service`, or the
   `default.target.wants` symlink directly — and verify
   `systemctl --user is-enabled oo7-daemon` on the smoke's first boot.
   Note `ImportCredential=oo7.keyring-encryption-password` in the unit:
   the unlock credential comes from PAM, so the daemon without the PAM
   flow is decorative.
4. **Migration test before shipping**: a machine with an
   autologin-produced passwordless login keyring, upgraded or re-imaged —
   the exact rhbz 2538274 shape — must end with the vault able to store
   and read a secret. If the upstream fix (issue #572, commits b236c6fb /
   78bb59f) doesn't cover the passwordless case, this lane is a NO-GO.
5. **No vault change needed** — the client already speaks both dialects
   (`6de80bc`). That is the one part of this switch that is free.
