# 45.0.0 pre-code testing — the rebase questions answered by hand, before any code

Status: written 2026-11-04. Companion to notes/45.0.0-ga-verification.md (the
post-GA re-check) and notes/45.0.0-upgrade-path-research.md (the ride plan).
This file is the hands-on pass: the two unresolved research questions and the
"beta-stage verify" items that could be answered without writing the rebase
were answered by pulling the GA `:45` image and probing it in a container, plus
registry/gitlab checks. Image under test:
`quay.io/fedora/fedora-bootc@sha256:8076cf4ff9d1fda1fcc759c021b8c317fe2b687ae51259e45917c95fed3308bc`
(os-release VERSION_ID=45). Labels: CONFIRMED = run/observed on 2026-11-04.

## Verdict

**Nothing found blocks writing the rebase. Both unresolved research items are
resolved in kuma's favor, and one new required change surfaced**: F45's Fedora
repo no longer ships `mesa-va-drivers` at all — mesa 26.x folded VA drivers
into `mesa-dri-drivers` — so the mesa block's Fedora-side package name is dead
and the block needs its install line reworked, not just re-verified. The RPM
Fusion URL install works non-interactively under enforced signatures (resolved
research question (a)), `mesa-va-drivers-freeworld` still exists in RPM Fusion
and installs cleanly, repoquery behaves exactly as updates.rs invokes it, and
bootc 1.17.x carries nothing that touches kuma's verbs.

## 2. RPM Fusion URL install under `%_pkgverify_level=all` — works, resolves research question (a) (CONFIRMED)

- The image confirms the enforced default: `rpm -E %_pkgverify_level` → `all`.
- Running the blocks.rs:311 shape in the image — `dnf5 -y install
  https://mirrors.rpmfusion.org/free/fedora/rpmfusion-free-release-45.noarch.rpm`
  — **completed, exit 0, non-interactive**. Output line: "Warning: skipped
  OpenPGP checks for 1 package from repository: @commandline". No key was
  imported and no `--nosignature` was passed: dnf5 5.4.6.0 (the #2479 fix
  generation) downgrades the @commandline verify failure to a warning rather
  than refusing.
- Consequence for kuma: the URL install works as written. No key-import
  pre-step is required. Worth a one-line comment in the block: the release RPM
  rides TLS trust, not signature trust — acceptable for a release RPM fetched
  over https, now stated rather than assumed.
- The rpmfusion .repo files land in `/usr/share/dnf5/repos.d/` alongside
  Fedora's (CONFIRMED in-container).

## 3. NEW: `mesa-va-drivers` is gone from Fedora 45 — the block must change (CONFIRMED)

- `dnf5 repoquery "mesa-va*"` against the F45 repos: **empty**. Fedora's mesa
  26.2.x no longer builds a `mesa-va-drivers` subpackage — the VA drivers are
  inside `mesa-dri-drivers`, which Provides `mesa-va-drivers` (CONFIRMED via
  `repoquery --whatprovides`).
- Observed dnf5 behavior: `dnf5 -y install mesa-va-drivers` exits 0 and
  installs mesa-dri-drivers (name resolved as a capability), but `rpm -q
  mesa-va-drivers` reports not-installed — a silent name→capability rewrite
  that would make the block's assert meaningless on the Fedora side.
- RPM Fusion's side is fine: `mesa-va-drivers-freeworld` exists for F45
  (26.2.3-1 in release, 26.2.6-1 in updates) and `dnf5 -y install
  mesa-va-drivers-freeworld --allowerasing` completes exit 0 in one
  transaction — no vendor-change warning, no erase needed (there is no Fedora
  mesa-va-drivers left to erase on F45; `--allowerasing` is harmless residue).
- What the rebase must do: rework the mesa block's install/verify lines for
  F45 — install `mesa-dri-drivers` (or just the freeworld package; its deps
  pull what's needed) and assert `mesa-va-drivers-freeworld` is installed with
  the freeworld VA driver files present, dropping any assertion on the dead
  Fedora-side package name. This was invisible to the research passes because
  both checked that RPM Fusion *ships* the freeworld name — neither checked
  that Fedora still ships the counterpart being erased.

## 4. repoquery / update --check surface — matches updates.rs's calls (CONFIRMED)

- `dnf5 repoquery --available -q kernel` → both 7.2.11-300 (GA) and
  7.2.15-300 (updates) returned. `dnf5 -q repoquery --latest-limit 1` →
  7.2.15-300. `repoquery --advisory-severities=important --latest-limit 2` →
  exit 0 with zero results (no important kernel advisories yet — the empty
  result is a valid answer, exit 0, which is what updates.rs's set -e contract
  needs to distinguish from an offline failure).
- Metadata loads from the relocated `/usr/share/dnf5/repos.d` (CONFIRMED; the
  repos themselves resolve — Fedora 45 + Updates loaded over the network).
- One transient observed twice: `mirrors.fedoraproject.org` metalink fetches
  reset the connection from this egress ("Recv failure: Connection reset by
  peer"); the shipped `baseurl=`-style repo definitions recovered both times.
  Same egress-hostility family as the ffmpeg.org block; the base image's
  baseurl entries are the reason it self-heals.
