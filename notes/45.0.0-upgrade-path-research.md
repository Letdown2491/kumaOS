# 45.0.0 upgrade-path research — what F44→F45 changes under the machine

This is the UPGRADE-PATH lens only (the kernel/fbcon/bootc-image/package-rename
side lives in notes/fedora-45-rebase.md and is not repeated here). Verdict up
front: **the 44→45 rebase looks mechanically safe for kumaOS, and unusually
quiet on the layers we pin.** bootc is the identical version on both sides
(1.16.13), so is greenboot (0.16.4) and rpm-ostree (2026.3) — the upgrade is
the ordinary `bootc switch` to a new tag, same staged-deployment + fallback
machinery as any 44.x ride. The real deltas are one major systemd jump
(259.9 → 262), OpenSSH 10.2→10.5 under crypto-policies 20260713, NetworkManager
1.56→1.58, firewalld 2.4.4→2.5.2 (bug-fix only), and selinux-policy 44.11→45.20.
None of these touches a pinned value in the boot smoke's floor: every sysctl and
karg we pin still exists at those versions, `systemd.ssh_auto=no` survives (the
ssh-generator is still in 262), and firewalld 2.5 changed no zone/rich-rule
semantics. The one known new hazard is SELinux AVC noise on F45
(io.systemd.NamespaceResource denials) — expected to be log noise, not
breakage, and it hits stock Silverblue too. The ride should be a normal
multi-day soak with the existing smoke as the gate, not a new test design.

Versions are cited two ways: measured on this host (the F44 reference, kumaOS
44.9.0, via `rpm -q`) and read out of the Fedora 45 development repo
(mirrors.kernel.org/fedora/development/45/, the post-beta branched tree —
versions there can still move before GA 2026-10-27).

| Component | F44 (measured on host) | F45 dev repo | Delta |

## 1. How a bootc 44→45 upgrade actually behaves, and what can break

The mechanics do not change with the Fedora major. `bootc switch`/`bootc
upgrade` to a 45-based image pulls the new bootable OCI, stages it as a new
ostree deployment, and the fallback deployment stays bootable until a new one
is successfully booted — the two-deployment model with staged deployments and
automatic rollback on failed boot is a property of ostree's deployment layout,
not of the Fedora release
(<https://ostreedev.github.io/ostree/deployment/>, CONFIRMED as general
mechanics). bootc is the same package version in F44 and F45 (both
1.16.13-1, CONFIRMED: measured on host; dev-repo Packages/b listing
<https://mirrors.kernel.org/fedora/development/45/Everything/x86_64/os/Packages/b/>),
so there is no bootc-side behavior change to absorb at the boundary.

rpm-ostree is likewise identical (2026.3-2 both sides, CONFIRMED: host
`rpm -q rpm-ostree`; dev-repo Packages/r listing
<https://mirrors.kernel.org/fedora/development/45/Everything/x86_64/os/Packages/r/>).
This also retires a peer-distro worry: notes/peer-distros-research.md's claim
that F45 ships a downlevel shell greenboot 0.15.8 is wrong — F45 dev ships
greenboot 0.16.4-0.fc45, the same Rust rewrite F44 already runs (CONFIRMED:
host `rpm -q greenboot`; dev-repo Packages/g listing
<https://mirrors.kernel.org/fedora/development/45/Everything/x86_64/os/Packages/g/>).

Breakers to actually check before the ride, none confirmed:

- **RPM repo configs moving /etc → /usr** ("Relocate RPM repository configs to
  /usr", approved F45 system-wide change,
  <https://fedoraproject.org/wiki/Releases/45/ChangeSet>, CONFIRMED as an
  approved change). For a bootc appliance this only matters if anything in our
  image writes to `/etc/yum.repos.d` expecting it to shadow the packaged
  config; our containerfile ships its own repos inside the image, so this is a
  check-then-move-on item, not a known break.
- **bootloader-update.service / bootc-base-imagectl**: nothing in the F45 dev
  tree or bootc 1.16.x release notes indicates a new mandatory bootc
  bootloader-refresh step for existing GRUB-based systems (UNVERIFIED — bootc
  GitHub release notes for 1.16.x not exhaustively re-read; the sealed-UKI test
  images are a separate opt-in artifact, see §2).
- **Incompatible /etc handling**: bootc has always left `/etc` (and `/var`)
  carried across deployments; the 44→45 switch does not reset any of
  faillock.conf, chrony, firewalld runtime config, or the ssh host keys the
  smoke depends on (CONFIRMED as general bootc behavior via the bootc/ostree
  deployment docs above).

## 2. UKI-by-default and `/usr/lib/bootc/kargs.d/`

UKI is **not** default in F45 and not something the rebase pulls us into. What
F45 adds is a *separate* slim UEFI-only GRUB2 package aimed at confidential
VMs that boot UKIs via BLS — additional, not replacement; FESCo approved
5-0-4 (<https://lwn.net/Articles/1085609/>, CONFIRMED). Separately, the
"sealed Atomic desktops" test images (systemd-boot + UKI + composefs) are
opt-in test artifacts, UEFI-only, explicitly not defaults
(<https://fedoramagazine.org/sealed-atomic-desktops-test-images/>, siosm,
2026-04-27, CONFIRMED as opt-in test images). kumaOS stays GRUB + BLS + kargs.d
in 45.0.0.

The kargs.d merge behavior we rely on is a bootc/container thing, not a
Fedora-release thing, and bootc is version-identical across the boundary:
drop-ins under `/usr/lib/bootc/kargs.d/` are merged into the kernel args of
new deployments, and our two files (`05-kuma-hardening.toml`,
`10-kuma-desktop.toml`) keep working unchanged. There is no F45 change
proposal to the kargs.d mechanism that I could find (UNVERIFIED beyond a
negative search of the F45 ChangeSet, <https://fedoraproject.org/wiki/Releases/45/ChangeSet>).
The existing smoke assertion — pinned kargs read back from `/proc/cmdline`
(scripts/smoke.sh ~3430-3476) — is the gate that would catch any merge
regression on the day, which is the right place for it.

## 3. The systemd delta: 259.9 → 262

This is the largest single jump and deserves the most soak attention. F44
ships systemd 259.9 (measured on host, CONFIRMED); F45 dev ships 262-3
(dev-repo Packages/s listing, CONFIRMED). Release facts:

- 258 (2025-09-17) and 259 (2025-12-18) we already live with — notably 259's
  default journal `Storage=persistent` and the ssh-generator whose existence
  is why we pin `systemd.ssh_auto=no` (F44 ships 259.9, so that karg is proven
  on the exact generator version family that motivated it). Sources: LWN
  <https://lwn.net/Articles/1051235/>; upstream 258 announcement
  <https://lists.freedesktop.org/archives/systemd-devel/>; version table
  <https://versio.io/releases/systemd> and the 2026 systemd deep-dive at
  <https://goranstimac.com> (REPORTED for 259 specifics).
- 260 (2026-03-17) **removed systemd-sysv-generator and rc-local-generator** —
  SysV init-script support is gone (REPORTED via the same version
  table/deep-dive). kumaOS ships no SysV init scripts and no
  /etc/rc.local; nothing to do, but if the smoke's journal ever shows
  rc-local-generator noise, this is why it disappeared rather than broke.
- 261 (2026-06-19) and 262 (2026-09-22) are ordinary minor releases in this
  reading; no feature or removal relevant to our pinned surface surfaced in
  the sources consulted (UNVERIFIED — 261/262 release notes not read line by
  line; flag for the soak).

What the jump cannot break: `systemd.ssh_auto=no` still parses — the
ssh-generator exists through 262 in every source consulted, and the karg is
harmless if unknown in any case (kargs unknown to a kernel are passed to
init). The smoke pins the observable outcomes (ssh does not auto-start at
boot before provision, journal behaves, unit graph comes up), so the boot
smoke is the right gate and needs no change for the version jump itself.

## 4. NetworkManager and firewalld

**NetworkManager 1.56.1 → 1.58.1** (CONFIRMED both sides: host rpm; dev-repo
Packages/n listing <https://mirrors.kernel.org/fedora/development/45/Everything/x86_64/os/Packages/n/>,
build dated 2026-10-12). Two behavioral notes from NM 1.57+: a
`nmcli device set ... managed --permanent down` semantics change
(<https://access.redhat.com/solutions/714498>, REPORTED — paywalled; verify
against the NM 1.58 release notes when the ride is planned) and the retirement
of the NM-fortisslvpn/NM-vpnc plugins in F45
(<https://www.linuxsecurity.com/> advisory feed, REPORTED). kumaOS uses
keyfiles generated at image build and does not touch those plugins; no
pinned smoke value depends on NM beyond the interface coming up.

**firewalld 2.4.4 → 2.5.2** (CONFIRMED both sides: host rpm; dev-repo
Packages/f listing <https://mirrors.kernel.org/fedora/development/45/Everything/x86_64/os/Packages/f/>).
Upstream 2.5.0 is a feature release but its features are a config-watcher
warning, a dark-theme GTK thing, and a Solr service; 2.5.1 and 2.5.2 are
bug-fix-only. The nftables backend and zone/rich-rule semantics are
unchanged; the closest-to-our-lane fixes are "OUTPUT and POSTROUTING should
terminate with ACCEPT" (2.5.1) and "prerouting cannot reliably determine
egress" (2.5.2), both about forwarded traffic we do not do
(<https://github.com/firewalld/firewalld/releases>, CONFIRMED for the
release contents). Our public zone contract — mdns + dhcpv6-client services,
the rich rule accepting ssh from 10.0.2.2/32, ssh service otherwise dropped
(blocks.rs FIREWALLD_PUBLIC_ZONE ~3841) — maps 1:1 onto 2.5.x configuration;
the smoke's assertions (public zone must NOT serve ssh, MUST contain the
rich rule) remain the gate and need no edits.

## 5. SELinux policy: 44.11 → 45.20

selinux-policy-targeted-45.20-1.fc45 is in the F45 dev repo (CONFIRMED,
Packages/s listing); the host runs 44.11-1 (CONFIRMED, measured). A
detailed per-module changelog for the 45.x series (xdm_t/greetd, journal
domains, podman, sshd_t) was not retrievable from a primary source this pass
(UNVERIFIED — src.fedoraproject.org is behind Anubis and the upstream
Changelog was not diffed per release). What is known:

- There is a real, observed AVC-noise regression on F45: denials against
  `/run/systemd/io.systemd.NamespaceResource` from NetworkManager and a batch
  of systemd services, plus systemd-tpm2 log denials, reported on Silverblue
  45 with bootc+UKI and on standard Workstation
  (<https://discussion.fedoraproject.org/t/fedora-45-selinux-problems/202886>,
  REPORTED — user reports, not a bug tracker verdict). New installs reportedly
  don't show the NamespaceResource set, so this smells like a relabel/ordering
  interaction, not a policy hole a single image can fix.
- Expectation for kumaOS: upgrade-day `journalctl -b | grep -i avc` will be
  noisier than the 44.x baseline. Treat new AVCs as a soak finding to triage
  (audit2allow upstream or setsebool), not an automatic rollback trigger —
  the smoke's SELinux-relevant assertions (ssh in via BatchMode with the
  0600 key, greetd/greeter chain reaching a session) pass or fail on real
  policy behavior, so the smoke still decides.

## 6. OpenSSH 10.2p1 → 10.5p1 under crypto-policies 20260713

openssh-10.5p1-1.fc45 is in the dev repo (CONFIRMED,
<https://mirrors.kernel.org/fedora/development/45/Everything/x86_64/os/Packages/o/>;
upstream released 10.6 on 2026-10-06, so F45 will likely take a 10.6.x update
shortly after GA — <https://www.openssh.com/releasenotes.html>, CONFIRMED).
Release notes 10.3 → 10.5, read for our usage (BatchMode pubkey auth from the
smoke, faillock in front of sshd):

- Nothing in 10.3–10.5 changes key-auth or BatchMode behavior. The changes
  that touch auth at all: 10.3 adds an `invaliduser` PerSourcePenalty and
  stops treating empty-cert principals as wildcard; 10.4 makes seccomp/NNP
  failures fatal in sshd and refactors sshd_config parsing (a PAMServiceName
  Match regression, fixed in 10.5); 10.5 requires ECC in libcrypto and applies
  authorized_keys `restrict` to tunnel forwarding (CONFIRMED,
  <https://www.openssh.com/releasenotes.html>). All upstream; the Fedora
  packaging keeps PAM stack and faillock wiring as it is.
- crypto-policies 20260713 (F45) vs 20251128 (F44) — CONFIRMED versions from
  the dev repo Packages/c listing and host rpm. The git log between them shows
  additions only: an openssh `mldsa44-ed25519` algorithm entry ("Requires
  OpenSSH 10.4" — and F45 has 10.5, so it's live), a NO-HMAC-SHA1 policy
  module, SLH-DSA OpenPGP support, FIPS/OSPP adjustments
  (<https://gitlab.com/redhat-crypto/fedora-crypto-policies/-/commits/master>,
  CONFIRMED commit list). Nothing removes ed25519 or tightens the DEFAULT
  policy in a way that would refuse our key exchange; NTS-backed chrony is
  untouched by both.
- One real sshd behavior note for the smoke itself: 10.4+ emits mixed-case
  `sshd -G` output and 10.6 adds a `WarnWeakCrypto` default-on server log —
  neither affects BatchMode key auth (CONFIRMED, release notes above).

## 7. Kernel kargs, modules, and the hardening floor

The companion file covers the kernel generally (7.2 line, kmscon/fbcon), so
narrow scope here: does anything our floor pins disappear in F45?

- The pinned kargs (init_on_free=1, page_alloc.shuffle=1, vsyscall=none,
  vdso32=0, module.sig_enforce=1, rd.shell=0, rd.emergency=halt,
  systemd.ssh_auto=no, random.trust_cpu=off — blocks.rs HARDENING_KARGS ~3816)
  are all upstream kernel/systemd parameters with no F45-side removal; the
  kernel 7.2 line accepts all of them (CONFIRMED for the parameter names as
  current kernel docs; UNVERIFIED against F45's exact GA kernel build, which
  is the boot smoke's `/proc/cmdline` assertion's job on the day).
- The pinned sysctl floor in the smoke (`1 2 3 1 0 0 32 2 0 1` for
  ptrace_scope/kptr_restrict/perf_event_paranoid/kexec_load_disabled/
  suid_dumpable/unprivileged_userfaultfd/mmap_rnd_bits/bpf_jit_harden/
  sysrq/icmp_echo_ignore_all) — all ten sysctls still exist in the 7.2 kernel
  and none was removed or renamed in any 7.2.x changelog consulted
  (UNVERIFIED exhaustively; CONFIRMED for existence in 7.2, which is what the
  smoke asserts). Notably, F45 makes restricted ptrace a *distribution
  default* ("Restricted ptrace by default" in the Beta announcement,
  <https://www.redhat.com/en/blog/fedora-45-beta-now-available>, CONFIRMED) —
  F45 is converging on what kumaOS already pins, so our floor stays stricter
  or equal, never looser, across the rebase.
- Kernel module renames/availability changes are the companion file's
  territory; nothing in the upgrade-path sources consulted touches a module
  kumaOS pins (CONFIRMED-negative for vgem-adjacent items: the smoke builds
  vgem out of tree already, per the CI history).

## 8. greenboot and rpm-ostree deltas

None. greenboot is 0.16.4-0 on both F44 and F45 (CONFIRMED, host rpm and
dev-repo Packages/g listing) — the Rust rewrite shipped in F44 and carries
over unchanged, so the boot-counter/rollback verdict path the fleet timers
rely on is byte-for-byte the same code across the rebase. rpm-ostree is
2026.3-2 on both sides (CONFIRMED, host rpm and dev-repo Packages/r listing);
no greenboot↔bootc interface change exists to absorb. This is the quietest
part of the whole delta and removes the only stale claim in
notes/peer-distros-research.md about F45 greenboot.

## 9. The rollback story

Unchanged and stronger than it needs to be. The ostree deployment model
keeps the previous (44.9.0) deployment bootable as fallback through the
entire 45.0.0 soak; a failed boot or failed greenboot checks returns the
machine to the fallback deployment, and `bootc rollback` is the manual path
(<https://ostreedev.github.io/ostree/deployment/>, CONFIRMED as general
mechanics; greenboot's verdict wiring unchanged per §8). The release tag to
build the rollback pin from is the current `:niri-44.9.0` image tag — the
machine that produced a running 45.0.0 binary should be a named commit, and
the image the fleet can fall back to is the named 44.9.0 one. Nothing in the
44→45 delta (no bootc/greenboot/rpm-ostree change, no GRUB major bump —
2.12-66 → 2.12-81, same series, CONFIRMED via the g/ listing) touches the
rollback machinery itself.

## 10. Recommended upgrade sequence and pre-flight checks

Sequence (unchanged from any prior ride in shape; the content of the checks
is what 44→45 makes load-bearing):

1. Rebuild the F45-based image in CI with the kargs.d files
   (05-kuma-hardening, 10-kuma-desktop) unchanged; the compose-time kargs
   merge test (`cargo test`) is the first gate.
2. Verify the image's version stamps before any switch
   (`podman run --rm --entrypoint /usr/bin/kuma-shell localhost/kuma:candidate
   --version`), per the 44.9.0 lesson about silently stale staged binaries.
3. Switch one machine with `bootc switch` to the 45 tag; do not touch
   anything in /etc — the rebase inherits faillock.conf, chrony NTS config,
   and the firewalld runtime setup as-is.
4. Reboot into the staged deployment; let greenboot's boot counter run its
   course. If the first boot fails checks, the fallback deployment is the
   44.9.0 one and the machine self-rolls back.
5. Soak several days before fleet-wide. Watch specifically: AVC noise
   (§5 — expected), the journal under systemd 262 (§3), and NM behavior on
   the slirp interface (§4).

Pre-flight checks (all already exist in scripts/smoke.sh; the point is that
none needs new pinned values):

- `/proc/cmdline` carries every pinned karg — catches any kargs.d merge
  surprise on the new systemd/kernel pair.
- The ten-value sysctl floor reads back exactly — catches any kernel 7.2.x
  sysctl change under the F45 GA kernel.
- ssh in via BatchMode with the 0600 key — catches OpenSSH 10.5 +
  crypto-policies 20260713 refusals and any selinux-policy 45.x sshd_t
  regression at once.
- faillock present in `/etc/pam.d/system-auth` and `deny = 50` in
  faillock.conf — the /etc carry-over check that proves the PAM stack
  survived the rebase (the F45 PAM move itself is the other file's topic).
- firewalld public zone: no ssh service, rich rule for 10.0.2.2/32 present —
  the firewalld 2.5 contract check.
- chrony reports ≥2 NTS sources — the crypto-policies/chrony interaction
  check.
- greeter chain reaches a session — the selinux-policy 45.x xdm_t/greetd
  check that no primary-source changelog could give us in advance.

## What the 45.0.0 ride must do

- **kargs.d**: ship both files unchanged. No F45 change touches the kargs.d
  merge; the smoke's `/proc/cmdline` assertions are the gate. Add nothing for
  systemd 262 — `systemd.ssh_auto=no` is still valid and still wanted.
- **Boot smoke pinned values**: change none of them. Every sysctl and karg
  pinned survives the F45 systemd/kernel/openssh/firewalld deltas. The ride
  is a version-bump soak, not a floor revision.
- **Greenboot checks**: no changes. greenboot 0.16.4 is version-identical
  across the rebase; the boot-counter/verdict wiring needs nothing.
- **Fleet timers**: keep the battery/metered gates as-is. The ride is
  bandwidth-heavy (a full new bootable image), which the existing
  metered-gating already handles; nothing in the F45 delta changes timer
  semantics (no greenboot/rpm-ostree/bootc delta).
- **Rollback tag**: build the rollback pin from `:niri-44.9.0`. One machine
  soaks first, greenboot's automatic fallback is the safety net, and the
  release commit must be named before any image is installed.
- **New soak observations (not gates)**: AVC noise around
  io.systemd.NamespaceResource (triage or accept), systemd 262 journal/unit
  graph behavior, OpenSSH 10.6's WarnWeakCrypto log lines once F45 takes the
  10.6 update post-GA.
- **Doc hygiene**: correct notes/peer-distros-research.md's stale
  "F45 ships greenboot-0.15.8 shell implementation" claim (F45 ships
  0.16.4-0.fc45, same Rust rewrite as F44).
